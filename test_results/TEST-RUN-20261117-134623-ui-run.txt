HOW THIS RUN WAS ACHIEVED
1. Reading: the documents selected for this run were uploaded to LlamaExtract (LlamaIndex Cloud, cost_effective tier), which returns claims with the page and text they came from; each claim is tied to a stored chunk and kept only if its value appears in that chunk text.
2. Ledger: accepted claims are stored in the claims table; the claims are sorted by label and sent to the LLM in batches of up to 300,000 characters, which groups the ones that state the same attribute of the same subject (no code matching, no fixed number of documents or claims assumed).
3. Judging: a group whose claims all state the same value counts as corroboration; every other group goes to the LLM, several groups to a call, in batches of up to 25,000 characters. The model gives one verdict per group: consistent when all its claims agree, a contradiction when any one differs.
4. Findings: a discrepancy is saved only if its quotes are exact substrings of their chunks (checked in code); per-document verdicts were skipped by request.
5. Model: gemini-3.5-flash-lite, temperature 0, up to 5 attempts per call honouring the provider's retry delay; no step, tool-call or finding limits.

KNOWN LIMITS OF THIS RUN
==============================================================================
- Reading is all-or-nothing per document: if one batch fails after all retries, that document's claims are discarded and it counts as not read.
- Candidate matching keeps at most 5 partners per claim (an existing default), so some comparable claims are never judged.
- The claim-extraction prompt lists business categories (capacity, supply, pricing, ...) and is not yet domain-agnostic.
- Claims inside one document are also grouped and judged; matching quality depends on how the model labels subject/metric/unit/period.
- Exact agreements are trusted as corroboration without an LLM check.
